# Well-Known Relations Reference

Complete reference documentation for relationships in the Backstage catalog.

## What are Entity Relations?

Entity relations define how catalog entities connect to each other. Relationships are automatically generated by the catalog based on entity specifications. Relations enable graph traversal, impact analysis, and understanding of dependencies.

## Ownership Relations

### ownerOf / ownedBy

Indicates ownership responsibility.

**Generated from:**

- `spec.owner` on Component, API, System, Domain, Resource

**Example:**

```yaml
# Component definition
spec:
  owner: group:pht-team/backstage-eng
# Generated relations:
# group:pht-team/backstage-eng -> [ownerOf] -> component:eng-tools/backstage
# component:eng-tools/backstage -> [ownedBy] -> group:pht-team/backstage-eng
```

**Query:** "What does this team own?" or "Who owns this component?"

## Composition Relations

### partOf / hasPart

Indicates hierarchical composition.

**Generated from:**

- Component `spec.system` → System
- Component `spec.domain` → Domain
- Component `spec.subcomponentOf` → Component
- API `spec.system` → System
- API `spec.domain` → Domain
- System `spec.domain` → Domain
- Resource `spec.system` → System
- Resource `spec.domain` → Domain

**Examples:**

```yaml
# Component belongs to system
spec:
  system: eng-tools/backstage
# Generated relations:
# component:eng-tools/backstage-dev -> [partOf] -> system:eng-tools/backstage
# system:eng-tools/backstage -> [hasPart] -> component:eng-tools/backstage-dev
```

```yaml
# System belongs to domain
spec:
  domain: product/platform
# Generated relations:
# system:eng-tools/backstage -> [partOf] -> domain:product/platform
# domain:product/platform -> [hasPart] -> system:eng-tools/backstage
```

**Queries:**

- "What systems belong to this domain?"
- "What components make up this system?"
- "What system does this component belong to?"

## Dependency Relations

### dependsOn / dependencyOf

Indicates functional dependencies.

**Generated from:**

- Component `spec.dependsOn` → Component or Resource

**Example:**

```yaml
# Component depends on another component and database
spec:
  dependsOn:
    - component:platform/auth-service
    - resource:eng-tools/backstage-db
# Generated relations:
# component:eng-tools/backstage -> [dependsOn] -> component:platform/auth-service
# component:platform/auth-service -> [dependencyOf] -> component:eng-tools/backstage
# component:eng-tools/backstage -> [dependsOn] -> resource:eng-tools/backstage-db
# resource:eng-tools/backstage-db -> [dependencyOf] -> component:eng-tools/backstage
```

**Queries:**

- "What does this component depend on?"
- "What components depend on this?"
- "Show me the dependency tree"

## API Relations

### providesApi / apiProvidedBy

Indicates API provisioning.

**Generated from:**

- Component `spec.providesApis` → API

**Example:**

```yaml
# Component provides APIs
spec:
  providesApis:
    - api:eng-tools/backstage-api
    - api:eng-tools/search-api
# Generated relations:
# component:eng-tools/backstage -> [providesApi] -> api:eng-tools/backstage-api
# api:eng-tools/backstage-api -> [apiProvidedBy] -> component:eng-tools/backstage
# component:eng-tools/backstage -> [providesApi] -> api:eng-tools/search-api
# api:eng-tools/search-api -> [apiProvidedBy] -> component:eng-tools/backstage
```

**Queries:**

- "What APIs does this component provide?"
- "Which component provides this API?"

### consumesApi / apiConsumedBy

Indicates API consumption.

**Generated from:**

- Component `spec.consumesApis` → API

**Example:**

```yaml
# Component consumes APIs
spec:
  consumesApis:
    - api:platform/auth-api
    - api:infrastructure/metrics-api
# Generated relations:
# component:eng-tools/backstage -> [consumesApi] -> api:platform/auth-api
# api:platform/auth-api -> [apiConsumedBy] -> component:eng-tools/backstage
# component:eng-tools/backstage -> [consumesApi] -> api:infrastructure/metrics-api
# api:infrastructure/metrics-api -> [apiConsumedBy] -> component:eng-tools/backstage
```

**Queries:**

- "What APIs does this component consume?"
- "Which components consume this API?"

## Group Relations

### memberOf / hasMember

Indicates group membership.

**Generated from:**

- User `spec.memberOf` → Group
- Group `spec.members` → User (inferred)

**Example:**

```yaml
# User is member of group
spec:
  memberOf:
    - group:pht-team/backstage-eng
# Generated relations:
# user:opentext/dserres -> [memberOf] -> group:pht-team/backstage-eng
# group:pht-team/backstage-eng -> [hasMember] -> user:opentext/dserres
```

**Queries:**

- "Who are members of this group?"
- "What groups is this user a member of?"

### childOf / parentOf

Indicates group hierarchy.

**Generated from:**

- Group `spec.parent` → Group

**Example:**

```yaml
# Child group
spec:
  parent: group:pht-team/common-tools
# Generated relations:
# group:pht-team/backstage-eng -> [childOf] -> group:pht-team/common-tools
# group:pht-team/common-tools -> [parentOf] -> group:pht-team/backstage-eng
```

**Queries:**

- "What teams report to this group?"
- "What group does this team report to?"

### leadOf / leaderOf

Indicates group leadership.

**Generated from:**

- Group `spec.leader` → User

**Example:**

```yaml
# Group leadership
spec:
  leader: user:opentext/dserres
# Generated relations:
# user:opentext/dserres -> [leadOf] -> group:pht-team/backstage-eng
# group:pht-team/backstage-eng -> [leaderOf] -> user:opentext/dserres
```

**Queries:**

- "Who leads this group?"
- "What groups does this person lead?"

## Contact Relations

### supportContact / supportContactFor

Indicates support contact assignment.

**Generated from:**

- Component `spec.supportContact` → User or Group
- API `spec.supportContact` → User or Group
- System `spec.supportContact` → User or Group
- Domain `spec.supportContact` → User or Group
- Resource `spec.supportContact` → User or Group

**Example:**

```yaml
# Support contact as user reference
spec:
  supportContact: user:opentext/platform-lead
# Generated relations:
# component:eng-tools/backstage -> [supportContact] -> user:opentext/platform-lead
# user:opentext/platform-lead -> [supportContactFor] -> component:eng-tools/backstage
```

**Queries:**

- "Who should I contact for support?"
- "What entities is this person supporting?"

## Relation Types Summary

| Relation       | Reverse           | Generated From           | Example                  |
| -------------- | ----------------- | ------------------------ | ------------------------ |
| ownerOf        | ownedBy           | spec.owner               | Team owns Component      |
| partOf         | hasPart           | spec.system, spec.domain | Component in System      |
| dependsOn      | dependencyOf      | spec.dependsOn           | Component needs Resource |
| providesApi    | apiProvidedBy     | spec.providesApis        | Component provides API   |
| consumesApi    | apiConsumedBy     | spec.consumesApis        | Component uses API       |
| memberOf       | hasMember         | spec.memberOf            | User in Group            |
| childOf        | parentOf          | spec.parent              | Group under Group        |
| leadOf         | leaderOf          | spec.leader              | User leads Group         |
| supportContact | supportContactFor | spec.supportContact      | User supports Entity     |

## Common Queries

### Finding Dependencies

"What does component X depend on?"

```
component:eng-tools/backstage
  -> [dependsOn] -> ?
```

### Finding Dependents

"What depends on component X?"

```
? -> [dependencyOf] -> component:eng-tools/backstage
```

### Finding API Consumers

"Who uses this API?"

```
? -> [consumesApi] -> api:platform/auth-api
```

### Finding Team Composition

"What's in this domain?"

```
domain:product/platform
  <- [partOf] -> system:*
  <- [partOf] -> component:*
```

### Finding Organizational Structure

"What's the hierarchy under this group?"

```
group:pht-team/common-tools
  <- [parentOf] -> group:pht-team/backstage-eng
  <- [parentOf] -> group:pht-team/devx
```

## Tips

- All relations are bidirectional (have reverse relations)
- Relations are computed at entity import time
- Relations enable powerful graph queries and visualizations
- The catalog UI uses relations to show connections
- Dependencies help identify impact of changes
- Ownership clarifies accountability
- Composition shows organizational structure
- API relations enable interface-based thinking
